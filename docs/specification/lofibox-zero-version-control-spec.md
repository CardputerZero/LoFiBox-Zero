# LoFiBox Zero Version Control Specification

## 1. Purpose

This document defines how `LoFiBox Zero` manages its software version number across the entire project — build system, C++ source, Python helpers, Debian packaging, and AppStream metadata.

The project targets Debian official repository inclusion. Version numbers must be strictly controlled, with a single source of truth and deterministic propagation to every consumer. Hardcoded version strings in any source file are forbidden.

For the version bump procedure, see Section 7. For Debian-specific compliance rules, see Section 8.

## 2. Single Source of Truth

The project version is defined in exactly one place:

```cmake
# CMakeLists.txt line 5
project(LoFiBoxZero VERSION 0.2.0 LANGUAGES C CXX)
```

`PROJECT_VERSION` is the authoritative version string. CMake also decomposes it into `PROJECT_VERSION_MAJOR`, `PROJECT_VERSION_MINOR`, and `PROJECT_VERSION_PATCH`, though current consumers all use the full string.

No other file — C++ source, Python script, shell script, packaging metadata, or documentation template — may define the version independently. The version must flow outward from `CMakeLists.txt` through automated mechanisms only.

## 3. Propagation: CMake → C++ Preprocessor

CMake injects the version into C++ via a `PUBLIC` compile definition on the core library:

```cmake
target_compile_definitions(lofibox_zero_core PUBLIC
    LOFIBOX_VERSION="${PROJECT_VERSION}"
)
```

Because the definition is `PUBLIC` on `lofibox_zero_core`, every library and executable that links it — transitively or directly — inherits the `LOFIBOX_VERSION` preprocessor macro:

| Target | Link Relationship | Receives LOFIBOX_VERSION |
|--------|-------------------|--------------------------|
| `lofibox_zero_core` | defines it PUBLIC | Yes |
| `lofibox_zero_target_cli` | links core | Yes (inherits via PUBLIC) |
| `lofibox_zero_host_runtime` | links core | Yes (inherits via PUBLIC) |
| `lofibox_webui` | links core | Yes (inherits via PUBLIC) |
| `lofibox_zero_x11` | links core | Yes (inherits via PUBLIC) |
| `lofibox_zero_device` | links core | Yes (inherits via PUBLIC) |
| `lofibox_zero_tui` | links core | Yes (inherits via PUBLIC) |

Every C++ consumer must use the same pattern — a preprocessor conditional with a safe fallback:

```cpp
#if defined(LOFIBOX_VERSION)
constexpr std::string_view kVersion{LOFIBOX_VERSION};
#else
constexpr std::string_view kVersion{"unknown"};
#endif
```

The `"unknown"` fallback exists as a build-system safety net. If the macro is absent due to misconfiguration, the binary degrades gracefully to `"unknown"` rather than displaying stale hardcoded text or failing to compile. The fallback must never become a convenient default that masks a missing compile definition in CI or packaging.

## 4. Propagation: CMake → Python

Python helper scripts cannot consume C preprocessor macros. They receive the version through CMake's `configure_file()` mechanism:

**Template** (`cmake/version.py.in`):
```python
# Generated by CMake — do not edit by hand.
LOFIBOX_VERSION = "@PROJECT_VERSION@"
```

**CMake generation and installation**:
```cmake
configure_file(
    "${PROJECT_SOURCE_DIR}/cmake/version.py.in"
    "${CMAKE_BINARY_DIR}/generated/version.py"
    @ONLY
)
install(FILES "${CMAKE_BINARY_DIR}/generated/version.py"
    DESTINATION "${LOFIBOX_PRIVATE_LIBDIR}"
)
```

The generated `version.py` is installed to `${LOFIBOX_PRIVATE_LIBDIR}` (`/usr/lib/lofibox/` on Debian). This directory is on the Python import path because `remote_media_tool.py` — also installed there — adds its parent directory via `sys.path.insert(0, str(script_dir))` before importing any provider modules.

**Python consumption** (example from `src/remote/jellyfin/jellyfin_provider.py`):
```python
try:
    from version import LOFIBOX_VERSION
except ImportError:
    LOFIBOX_VERSION = "0.0.0-dev"
```

The `try/except ImportError` fallback to `"0.0.0-dev"` serves two purposes:
- Development builds where `version.py` has not been installed to the expected path continue to run
- The `-dev` suffix makes it visually obvious in logs and User-Agent headers that this is not a release build

This approach is deterministic — given the same source tree and the same `PROJECT_VERSION`, the generated `version.py` is byte-identical across builds. This satisfies Debian's reproducible builds requirement.

## 5. Consumer Registry

Every location that displays or transmits the software version must derive it from one of the two automated propagation paths above. The following table records all current consumers:

| Consumer | File | Propagation | Display Format |
|----------|------|-------------|----------------|
| CLI `--version` | `src/targets/cli_options.cpp` | Preprocessor | `lofibox 0.2.0` |
| CLI `--version --machine-read` | `src/targets/cli_options.cpp` | Preprocessor | `{"name":"lofibox","version":"0.2.0"}` |
| CLI `--help` banner | `src/targets/cli_options.cpp` | Preprocessor | `LoFiBox 0.2.0` |
| GUI About page | `src/app/app_projection_builder.cpp` | Preprocessor | Rendered in 320×170 canvas |
| WebUI snapshot DTO | `src/webui/webui_projection.cpp` | Inherited via lofibox_zero_core | Not yet displayed in frontend; available in JSON |
| Jellyfin Auth header | `src/remote/jellyfin/jellyfin_provider.py` | configure_file() | `Version="0.2.0"` in `MediaBrowser` auth |
| Debian package | `debian/changelog` | Manual (see Section 7) | `lofibox (0.2.0-1)` |
| AppStream metadata | `data/io.github.vicliu624.lofibox.metainfo.xml` | Manual (see Section 7) | `<release version="0.2.0" .../>` |
| Debian watch | `debian/watch` | Tag pattern match | No version literal needed |

Any new consumer added to the project must be added to this registry.

## 6. App Version vs. Snapshot Version

Two distinct version concepts co-exist in the codebase and must not be confused:

| Concept | Type | Source | Semantics | Consumer Scope |
|---------|------|--------|-----------|----------------|
| **App version** | String (`"0.2.0"`) | `CMakeLists.txt` `PROJECT_VERSION` | Software release identity | CLI, GUI About, Jellyfin UA, Debian package, AppStream metadata |
| **Snapshot version** | Unsigned integer (`42`, `43`, …) | `RuntimeSnapshot::version` | Monotonic counter incremented on every runtime state mutation; used for cache invalidation and event diffing | Runtime event stream, WebUI event tracking, snapshot comparison |

The snapshot `version` field in WebUI JSON responses (e.g., `"version": 42` at the top level of `GET /api/runtime/snapshot`) is the runtime state counter, **not** the app release version. The WebUI frontend stores this as `state.version` for internal event-stream tracking. It must never be displayed to users as if it were the software version.

Code that names a variable `version` must document which of these two concepts it holds. When both appear in the same scope, use distinct names: `app_version` and `snapshot_version`, or `kVersion` (app) and `version` (snapshot, matching the `RuntimeSnapshot` field name).

## 7. Version Bump Procedure

When releasing a new version, the following files require manual update, in this order:

### 7.1 Single Source Change (required)

**`CMakeLists.txt`** — Update `project(LoFiBoxZero VERSION X.Y.Z …)`. This is the single change from which all automated propagation flows. All other version-bearing locations in C++ and Python are generated or preprocessor-derived and require no edit.

### 7.2 Downstream Manual Updates (required)

After changing `CMakeLists.txt`, these files must be manually updated to match:

1. **`CHANGELOG.md`** — Add a `## [X.Y.Z] — YYYY-MM-DD` section following the Keep a Changelog format (already established in the file). Sections: `### Added`, `### Changed`, `### Deprecated`, `### Removed`, `### Fixed`, `### Security`.

2. **`debian/changelog`** — Add a `lofibox (X.Y.Z-1) UNRELEASED; urgency=medium` entry following Debian Policy format. The first line must be `package (version) distribution; urgency=value`. Each change line must be indented by two spaces and start with `*`. The trailer must be `-- Maintainer Name <email>  Day, DD Mon YYYY HH:MM:SS +TZOFF`.

3. **`data/io.github.vicliu624.lofibox.metainfo.xml`** — Add a `<release version="X.Y.Z" date="YYYY-MM-DD">` entry as the first child of `<releases>` (newest first). Include a `<description>` child element summarizing the release changes. AppStream metadata is consumed by GNOME Software, KDE Discover, and the Debian archive metadata pipeline.

### 7.3 Locations That Require No Manual Edit

The following locations are automatically correct after a `CMakeLists.txt` version bump:

| Location | Mechanism | Verification |
|----------|-----------|-------------|
| `cli_options.cpp` (CLI --version, --help) | `LOFIBOX_VERSION` preprocessor macro | `lofibox --version` |
| `app_projection_builder.cpp` (GUI About page) | `LOFIBOX_VERSION` preprocessor macro | Navigate to About page |
| `jellyfin_provider.py` (Jellyfin User-Agent) | `configure_file()` from `version.py.in` | Check Jellyfin server logs |
| All other targets linking `lofibox_zero_core` | `LOFIBOX_VERSION` via PUBLIC inheritance | Rebuild + verify |

### 7.4 Post-Bump Verification

After a version bump, CI must verify:

- `lofibox --version` outputs the new version
- `lofibox --version --machine-read` outputs `{"version":"X.Y.Z"}`
- GUI About page renders the new version string
- `dpkg-buildpackage` produces a `.deb` with the new version in its filename
- `appstreamcli validate` passes on the updated metainfo file
- `debian/changelog` parse succeeds (`dpkg-parsechangelog`)

## 8. Debian Compliance

### 8.1 Upstream vs. Debian Version

The version in `CMakeLists.txt` is the **upstream version**. When packaged for Debian, the Debian maintainer appends the **Debian revision** (e.g., `0.2.0-1`) in `debian/changelog` only.

The upstream source must report the unadorned version string:
- `lofibox --version` → `lofibox 0.2.0` (not `lofibox 0.2.0-1`)
- GUI About page → `0.2.0` (not `0.2.0-1`)
- Jellyfin User-Agent → `Version="0.2.0"` (not `Version="0.2.0-1"`)

Any Debian-specific packaging version information belongs in the package metadata, not in the upstream source.

### 8.2 debian/watch

`debian/watch` must reference the upstream release tag pattern:

```
version=4
opts=filenamemangle=s/.+\/v?(\d\S*)\.tar\.gz/lofibox-$1\.tar\.gz/ \
  https://github.com/vicliu624/LoFiBox-Zero/tags .*/v?(\d\S*)\.tar\.gz
```

The tag name on the upstream repository (e.g., `v0.2.0`) must match the `CMakeLists.txt` version. A version bump must include a corresponding Git tag.

### 8.3 debian/changelog Format

`debian/changelog` must follow the Debian Policy format exactly. The version field must be `X.Y.Z-N` where `X.Y.Z` matches the upstream version and `N` is the Debian revision number (starting at 1 for each new upstream release).

The file is parsed by `dpkg-parsechangelog` during package builds. Malformed entries cause build failures. Common format errors to avoid:
- Missing blank line between the header line and the first change entry
- Change entries not indented by exactly two spaces
- Trailer date format not matching `Day, DD Mon YYYY HH:MM:SS +TZOFF`

### 8.4 AppStream Metadata

`data/io.github.vicliu624.lofibox.metainfo.xml` must list all releases in reverse chronological order (newest first). Each `<release>` entry must have `version` and `date` attributes. The version attribute value must match the upstream version string without any Debian revision suffix.

### 8.5 Reproducible Builds

Both version propagation mechanisms satisfy Debian's reproducible builds requirement:

- **Preprocessor macro**: `LOFIBOX_VERSION` is set at CMake configure time from `PROJECT_VERSION`. Given the same source tree and build flags, the resulting binary is bit-identical.
- **configure_file()**: The generated `version.py` is deterministic — same input template + same `PROJECT_VERSION` → byte-identical output.
- No build timestamp, username, hostname, or random identifier is embedded in version-bearing code paths.

## 9. Forbidden Patterns

The following patterns are forbidden and must be caught in code review:

- **Hardcoded version literals**: Any source file (C++, Python, shell, CMake helper) containing a literal version string such as `"0.2.0"` or `"0.1.0"`. The grep pattern `"0\.[0-9]+\.[0-9]+"` should return zero results in `src/` at all times.
- **Duplicate version definitions**: A second `project(VERSION …)` call, a hand-maintained `VERSION` file, a `version.txt`, or any alternative source of truth.
- **Build-time version detection**: `git describe`, `git rev-parse`, or any VCS-based version extraction in build scripts. The version must come from `CMakeLists.txt`, not from Git history.
- **Version in file names without automation**: If a file name must include the version (e.g., a tarball or `.deb`), it must be generated from `PROJECT_VERSION` rather than hand-typed.
- **Snapshot version displayed as app version**: `RuntimeSnapshot::version` (the integer state counter) must never appear in user-facing version displays.
- **Version embedded in binary via `__DATE__` or `__TIME__`**: These macros make builds non-reproducible and must not appear in version-bearing code paths.

## 10. AI Constraints

- Do not add a hardcoded version string to any source file. Always use the preprocessor macro or the generated `version.py` module.
- Do not add a second source of truth for the version number.
- Do not use `git describe` or any VCS-based version guessing in build scripts.
- Do not display `RuntimeSnapshot::version` to users as if it were the software version.
- When adding a new consumer that needs the software version, add it to the Consumer Registry (Section 5).
- When bumping the version, follow the Version Bump Procedure (Section 7) in exact order.
- Do not embed build timestamps, usernames, hostnames, or random identifiers in version-bearing code paths.
- If a build fails because `LOFIBOX_VERSION` is not defined, fix the CMake compile definition chain rather than working around it with a hardcoded fallback that masks the root cause.
